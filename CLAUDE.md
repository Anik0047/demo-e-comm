# Kenakata: project rules and design system

Read this file completely before writing or changing any code. Also read `AGENTS.md` (Next.js coding rules generated by create-next-app). If the two ever conflict on design or UI, this file wins.

## 1. Project overview

- **Product:** Kenakata, a multi-vendor e-commerce marketplace for Bangladesh (many independent vendors sell on one platform).
- **Scope right now:** frontend UI only. All data is static/mock. **No backend, no API calls, no database, no axios/fetch to external services.**
- **Four interfaces in one Next.js app:**
  1. Main website (customer-facing storefront: home, categories, products, cart, wishlist, checkout)
  2. Customer dashboard (profile, orders, addresses, wishlist, reviews, returns, notifications)
  3. Vendor panel (store profile, products, variations, inventory, orders, earnings, wallet, withdrawals)
  4. Admin panel (customers, vendor and product approval, categories, orders, payments, commissions, refunds, coupons, support)
- **Stack:** Next.js (App Router), TypeScript (strict), Tailwind CSS v4 (CSS-first, tokens live in `src/app/globals.css`, no `tailwind.config.js`), Lucide React, React Icons, pnpm.
- **Package manager:** pnpm only. Never use npm or yarn. Do not add a dependency without asking first.

## 2. How to work

1. Build **one section at a time** (for example Navbar, then Banner). After finishing a section, stop and wait for the user's review and confirmation before starting the next one.
2. Before building, state the section name and what you will build in 2 to 4 lines. Then build it.
3. When you finish, run `pnpm lint` and `pnpm build`, fix errors, and report what changed.
4. Do not refactor or restyle sections the user already approved unless asked.
5. If a request conflicts with this file (for example "add a gradient" or "add dark mode"), say so and ask before doing it.

## 3. Brand

- **Name:** Kenakata ("Kena" + "kata", Bangla for buying and selling). Always written `Kenakata`, one word, capital K.
- **Wordmark:** `Kena` in ink + `kata` in brand green, font Plus Jakarta Sans, weight 800, tight tracking.
- **Logo mark:** rounded-xl square (`bg-brand`, white shopping-bag icon from Lucide `ShoppingBag`). Sizes: 40px in the header, 36px compact.
- **Currency:** Bangladeshi taka, written `৳` before the amount with comma grouping: `৳4,850`. Always format with `formatPrice()` from `src/lib/utils.ts`.
- **Languages:** English first, Bangla (বাং) switch shown in the UI. When Bangla content is added, use Hind Siliguri or Noto Sans Bengali as the Bangla font and never use fixed widths on text containers.
- **Tone of copy:** friendly, plain, short. Sentence case for buttons, headings, and labels ("Free delivery on orders over ৳2,000", "Flash deals"). No ALL CAPS, no Title Case, no excessive exclamation marks.

## 4. Design theme

- **Style:** clean, bright, dense marketplace (in the spirit of large marketplaces) with soft rounded shapes. Lots of products and offers visible, but with generous whitespace so it never feels cluttered.
- **Light theme only.** The site is always light. Do not add dark mode, `dark:` classes, or `prefers-color-scheme` rules.
- **NO GRADIENTS. EVER.** This is a hard rule from the owner. Use flat solid colors only: backgrounds, buttons, text, borders, badges, overlays, skeleton loaders, charts, illustrations, and SVG. Do not use `bg-gradient-*`, `bg-linear-*`, `bg-radial-*`, `bg-conic-*`, `from-*`/`via-*`/`to-*`, `linear-gradient()`, `radial-gradient()`, or a shimmer sweep. If an overlay is needed on an image, use a flat `bg-black/40`.
- **Elevation:** prefer 1px borders over shadows. Use `shadow-lg` only on floating surfaces (dropdowns, mini-cart, popovers, modals).
- **Shapes:** controls 8px radius (`rounded-lg`), buttons and search fields fully rounded (`rounded-full`), cards and banners 16px (`rounded-2xl`), avatars and badges full.
- **Decoration:** solid circles, simple shapes, and Lucide icons. No stock illustrations, no textures, no blur effects.

- Status colors: success = `brand`, warning = `accent`, danger = `sale`, info = `info`.
- Use at most 2 to 3 colors in one component.

## 6. Typography

Fonts are loaded with `next/font/google` in `src/app/layout.tsx` and exposed as CSS variables.

- **Headings, wordmark, prices, numbers that need emphasis:** Plus Jakarta Sans (`font-head`), weights 500, 700, 800.
- **Body, UI labels, forms:** DM Sans (`font-body`, default on `body`), weights 400, 500, 700.
- **Only two families.** Do not add other fonts without asking.

| Role | Classes |
|---|---|
| Display / hero heading | `font-head font-extrabold text-3xl sm:text-5xl leading-tight` |
| h1 | `text-3xl sm:text-4xl lg:text-5xl font-extrabold` (set globally) |
| h2 (section title) | `text-2xl sm:text-3xl font-bold` (set globally) |
| h3 / card title | `text-xl sm:text-2xl font-bold` (set globally) |
| Body | `text-base` (16px), line-height 1.5 |
| Small / meta | `text-sm text-mute` |
| Caption / badge | `text-xs` |

- Never go below 12px. Product titles clamp to 2 lines with `line-clamp-2`.
- Use real typographic punctuation in visible copy: `’` for apostrophes and `“ ”` for quotes.

## 7. Layout and spacing

- **Container:** wrap every section's content in `<div className="container-page">` (max 1280px, 16px side padding).
- **Section rhythm:** use `section-y` (24px mobile, 40px desktop) between sections.
- **Grid:** 12-column grid with `gap-4` (16px). Product grids: 2 columns on mobile, 3 on `md`, 4 to 5 on `lg` and up.
- **Spacing scale:** stick to Tailwind steps 1, 2, 3, 4, 6, 8, 10, 12 (4px to 48px).
- **Mobile first.** Write base styles for 360px, then add `sm:` (640), `md:` (768), `lg:` (1024), `xl:` (1280). Test at 360, 768, and 1280.
- **Z-index scale:** category row dropdowns 20, sticky header 30, overlays and drawers 50, modals 60, toasts 70.
- **Header behavior:** only the main header row is sticky. The top strip and category row scroll away.

## 7b. Responsive requirements (mandatory for every section)

- Support every width from 320px to 1920px and landscape phones. The page must never scroll horizontally.
- Mobile first. Every grid has an explicit base template (`grid-cols-1` or `grid-cols-2`). Never use a bare `grid` that only defines columns at larger breakpoints.
- Add `min-w-0` to grid and flex children that contain text, carousels, search fields, or tables so they can shrink.
- No fixed widths wider than the container. Fixed pixel widths are only for small things (icons, avatars, dropdown panels that have a mobile fallback).
- Re-check type sizes at EVERY breakpoint. When a layout adds a sidebar or splits into columns (for example at `lg`), the content area can become narrower than on the breakpoint below it.
- Reserve space for absolutely positioned overlays (controls, badges). Content must clear them by at least 12px.
- Hover-only UI (dropdowns, mini-cart) must have a touch alternative or be hidden below `md`.
- Never hide horizontal overflow with `overflow-x-hidden` on `html`, `body`, or ancestors of sticky elements. Fix the cause.
- Test at 320, 360, 390, 414, 480, 640, 768, 820, 1024, 1100, 1280, 1440, 1920 and landscape 667x375.

## 8. Icons

- **Lucide React is the default** (`import { ShoppingCart } from "lucide-react"`). Import icons individually. Default stroke width 2. Sizes: 16, 20, or 24px (`size-4`, `size-5`, `size-6`).
- **React Icons only for brand logos** (social networks, payment brands such as bKash/Nagad if available) and anything Lucide does not have. Import from a specific pack, for example `react-icons/fa6`.
- Never use emoji as icons. Do not mix icon styles inside one group of controls.
- Icon-only buttons must have an `aria-label`. Decorative icons get `aria-hidden="true"`.

## 9. Component conventions

**Buttons** (classes from `globals.css`): `btn` + size (`btn-sm` 36px, `btn-md` 44px, `btn-lg` 48px) + variant.
- `btn-primary`: main action (one per view area)
- `btn-outline`: secondary action
- `btn-ghost`: tertiary and toolbar actions
- `btn-sale`: urgent or destructive actions
- Disabled buttons are avoided; show a clear message instead when possible.

**Inputs:** `input` class (44px tall, 8px radius). The header search is the exception: a full pill with the category selector inside it. Show errors inline under the field in `text-sm text-sale`. Use sentence-case labels above fields, real example text as placeholders.

**Cards:** `card` (white, 1px `line` border, 16px radius), add `card-hover` for clickable cards.

**Product card pattern (dense marketplace):**
- Square image area on `bg-soft` with `rounded-xl`, wishlist heart button at top right, discount `badge-sale` at top left
- Title: `text-sm font-medium line-clamp-2`; title has a minimum height of two lines so cards in a row have equal height
- Never use text smaller than 12px (`text-xs`)
- Price row: `price` (current), `price-old` (original), discount percent in `text-sale`
- Rating: amber star + number + review count in `text-xs text-mute`
- Vendor name in `text-xs text-mute`, links to the vendor store
- Add-to-cart appears as a full-width `btn-outline btn-sm` or an icon button

**Section header pattern:** `h2` on the left, "View all →" link on the right in `text-brand-strong font-bold text-sm`. Optional small subtitle in `text-mute`.

**Badges and status chips:** use `badge` + variant. Order and vendor statuses: pending = `badge-warning`, approved/delivered/paid = `badge-brand`, rejected/cancelled/failed = `badge-danger`, processing/shipped = `badge-info`, draft/inactive = `badge-neutral`.

**Dropdowns, mini-cart, popovers:** `popover` class, open on hover and on keyboard focus (`group-hover` + `group-focus-within`), 8px gap from the trigger with no dead zone.

**Carousels:** autoplay allowed only if it is pausable, pauses on hover and focus, supports swipe and arrow keys, and respects reduced motion.

**Tables (admin, vendor, customer dashboards):** `card` wrapper, header row `bg-soft text-xs font-bold text-mute`, rows separated by `border-line`, hover `bg-brand-tint`, sticky first column on mobile, horizontal scroll container for overflow, pagination at the bottom.

**Dashboards:** left sidebar (collapses to a drawer below `lg`), top bar with search and profile menu, stat cards in a grid of 2 (mobile) to 4 (desktop), content in `card` blocks.

**Toasts and feedback:** every simulated action (add to cart, approve vendor, save product) updates local state and shows a short toast like "Added to cart".

**Required states for every data-driven view:** loading (`skeleton`), empty (an invitation with a clear next action, not an apology), and error (what happened and what to do next).

**Forms:** validate with React Hook Form + Zod when forms are added (ask before installing). Validate on blur and submit, keep the user's input on error.

## 10. UI/UX guidelines

- **Accessibility:** semantic landmarks (`header`, `nav`, `main`, `footer`), one `h1` per page, visible `:focus-visible` ring (set globally), all interactive elements reachable by keyboard, touch targets at least 44px, meaningful `alt` text, `aria-label` on icon buttons, no information conveyed by color alone.
- **Motion:** transitions 150 to 200ms, ease-out. No bouncing or heavy parallax. Everything respects `prefers-reduced-motion` (handled globally).
- **Performance:** use `next/image` for all images with explicit sizes, `loading="lazy"` below the fold, server components by default.
- **Feedback:** hover states on every interactive element, clear active/selected states, instant visual response to clicks.
- **Hierarchy:** one clear primary action per area. Price and discount are the most prominent info on a product card.
- **Consistency:** reuse existing components before creating new ones. If a pattern appears twice, extract it into `src/components/shared`.
- **Mobile:** bottom-friendly actions, a drawer for navigation, search always reachable, no hover-only features.
- **Trust signals** (free delivery, cash on delivery, easy returns, secure payment) appear near the top of the home page and again at checkout.

## 11. Code conventions

- **Structure:**
  ```
  src/
    app/
      (storefront)/       main website
      (auth)/             login, register, forgot password
      (customer)/account/ customer dashboard
      vendor/             vendor panel
      admin/              admin panel
      globals.css
      layout.tsx
    components/
      ui/                 small reusable pieces (button wrappers, badge, rating, price)
      layout/             navbar, footer, dashboard shells
      home/               home page sections (banner, categories, deals)
      shared/             product-card, section-header, empty-state, toast
    data/                 static mock data (typed)
    services/             async functions that return mock data (the only place that touches /data)
    types/                shared TypeScript types (Product, Vendor, Order, User, Category ...)
    hooks/                custom hooks
    lib/utils.ts          cn(), formatPrice()
  ```
- **Components:** function components, PascalCase names, kebab-case file names (`product-card.tsx`), named exports for components, default exports only for `page.tsx`/`layout.tsx`. One component per file. Props typed with an `interface` named `<Component>Props`.
- **Client components:** add `"use client"` only where state, effects, or browser APIs are needed. Keep the client boundary as low in the tree as possible.
- **Styling:** Tailwind utility classes with the design tokens. Use `cn()` to combine classes. No inline `style` except for truly dynamic values. No CSS modules, no styled-components.
- **Data:** components never import raw data files. They call functions in `src/services` (for example `getProducts()`), which return typed mock data. When a real backend arrives, only the services change.
- **State:** local state for UI, React context or a small store for cart, wishlist, and fake auth later (persist to localStorage). Wrap every localStorage read and write in try/catch.
- **TypeScript:** strict mode, no `any`, no non-null assertions unless justified. Shared types live in `src/types`.
- **Imports:** use the `@/` alias (`@/components/...`). Order: React/Next, third party, internal, types.
- **Comments:** only where the code is not self-explanatory. Mark section boundaries in large files.
- **Do not:** add dark mode, add gradients, hardcode hex colors, call external APIs, install unrequested packages, or leave `console.log` in code.

## 12b. Category hierarchy (data model, keep in mind for all future work)

- Three levels: Category (level 1) → Subcategory (level 2) → Child category (level 3). Every subcategory belongs to exactly one category, and every child category belongs to exactly one subcategory.
- Model it as ONE flat list with `parentId` and `level` (see `src/types/category.ts`), not as three separate types or deeply nested objects. Main categories have `parentId: null`.
- `slug` is unique and URL-safe. Planned URLs: `/category/[category]`, `/category/[category]/[subcategory]`, `/category/[category]/[subcategory]/[child]`.
- Products will later reference the deepest category they belong to; parents are found through `parentId`.
- Current UI scope: only the 8 main categories are displayed (home page tiles). The Navbar mega menu still uses its own two-level data and will be connected to this hierarchy later. Do not build subcategory or child category UI until asked.

## 12c. Product data model

- Full `Product` type lives in `src/types/product.ts` (identity, relationships, media, pricing, variants, inventory, shipping, social proof, badges, moderation status, SEO, timestamps). Create products with `createProduct()` in `src/data/products.ts` so mock data stays short.
- `categoryId` points to the DEEPEST category the product belongs to (category, subcategory, or child category). Parents are found through `parentId`.
- Prices are whole taka (BDT). `price` is the regular selling price. The discount percentage is NEVER stored: calculate it with `calcDiscountPercent()`.
- A flash deal is a separate record (`FlashDeal`: productId, dealPrice, startsAt, endsAt, stockLimit, soldCount), not a field on the product. The service merges deal and product into a `FlashDealItem` where `price` is the deal price and `compareAtPrice` is the regular price.
- Lists use the small `ProductCardData` shape, not the full `Product`.
- Only products with `status: "active"` appear in the storefront.
- Countdown values come from the service as a number of seconds (`endsInSeconds`) so server and client render the same first frame.
